# Sandbox implementation: running a cloud session

> **To start a session**, give the cloud agent this prompt: "Resume the
> sandbox work by following `docs/plans/sandbox-sessions-cloud.md` on the
> `feat/sandbox-harness` branch. Do not open or edit any pull request."
> From T40 on, name `feat/sandbox-remove-jupyter` instead.

How an agent session in the cloud (Claude Code on the web, or any hosted
agent that clones this repository) picks up the sandbox work where the last
session left it, does the part a cloud machine can do, and hands it back.
It says nothing about what to build: that is
[sandbox-implementation.md](sandbox-implementation.md), the one
implementation plan, which both local and cloud sessions follow. Sessions on
the owner's laptop follow [sandbox-sessions-local.md](sandbox-sessions-local.md)
instead of this file.

Written 2026-11-10. The design being implemented is
[docs/history/sandbox-code-interpreter.md](../history/sandbox-code-interpreter.md).

## What a cloud session is for

Most of this work happens on the laptop, because the sandbox needs Docker,
KVM and the Kata runtime, and the harness needs the GPU. A cloud session is
for the parts that need none of them: backend code behind the
`SandboxBackend` interface tested against `FakeBackend`, frontend rendering
and its Vitest and Playwright tests, migrations, prompts, settings, and
docs. It never finishes a task alone when part of the task's verification
needs the laptop: it leaves the task at `needs-local-verify` and says
exactly what is left to check.

A cloud session does **not**:

- open, edit, comment on, label, mark ready or merge any pull request. The
  cloud platform appends a "Generated by" footer and a session link to PR
  bodies it writes, which the `PR gate` check rejects, and the draft PR's
  body is maintained by local sessions only;
- turn on auto-merge, or push to `main`;
- take a task whose **Author** tags include `kvm`, `gpu`, `host-internet`,
  `local` or `owner`, or `docker` unless the probe below shows a working
  Docker daemon (and even then the result is `needs-local-verify`: the
  laptop's Docker is the one that counts). A task whose Author tag is
  `any` but whose **Verify** tags need more is fine to take; it ends at
  `needs-local-verify`;
- rebase or force-push anything.

## The ledger is the only memory

A cloud session starts with nothing but a fresh clone. It has no
oh-my-claudecode plugin state (`.omc/` is gitignored and lives only on the
laptop), no previous conversation, and possibly a different set of tools.
Everything it needs to resume is in the **ledger** at the top of
`docs/plans/sandbox-implementation.md` on the feature branch: every task's
status, commit and evidence, the active-session claim, the session log and
the open owner questions. Everything it learns that the next session needs
goes back into that ledger, in a commit, before it stops.

The copies of these plan files on `main` (where a fresh clone starts) are
stale by design while the work is under way. Read them only to find the
branch; then read the branch's copies.

## Fixed names

| Thing | Value |
|---|---|
| Feature branch | the branch of the layer the next task belongs to, from the ledger header's table: `feat/sandbox-harness` for T30-T39, `feat/sandbox-remove-jupyter` for T40-T49 (`<feature-branch>` in the commands below) |
| Pull request | that layer's draft PR, one of four stacked PRs; each number is in the ledger header's table. Read it, never write to it |
| Owner's git identity | `Eli Pittman <123281783+epittman23@users.noreply.github.com>` (the identity on the owner's squash commits on `main`; not "the newest commit", which can be Dependabot's or a cloud session's) |

## Session start

1. **Get on the feature branch.**
   ```sh
   git fetch origin --prune
   git switch <feature-branch> 2>/dev/null \
     || git switch -c <feature-branch> --track origin/<feature-branch>
   git log --oneline -5
   ```
   If the branch does not exist yet, the draft PR has not been opened (task
   T00 is a local task). Stop and report that; do not create the branch.

   Some cloud platforms start the session on a branch of their own
   (`claude/...`) and only allow pushing to it. Find out now, not after the
   work: note the branch the session started on (`git branch
   --show-current` before switching) and the platform's instructions. If
   the platform requires its own branch, create that branch from the
   feature branch's tip (`git switch -C <platform branch>
   origin/<feature-branch>`) and work there. That is a
   **hand-off branch**: a local session merges it later.

2. **Set the owner's identity before any commit.** A cloud session's
   global git identity can be `Claude <noreply@anthropic.com>`; a squash
   merge would add a `Co-authored-by:` trailer for it on `main`, which the
   commit policy forbids and the `PR gate` does not catch (it reads
   messages, not authors).
   ```sh
   git config user.name  "Eli Pittman"
   git config user.email "123281783+epittman23@users.noreply.github.com"
   git config user.name; git config user.email
   ```
   Use exactly the identity in "Fixed names". Never derive it from
   `git log`: `main` also carries commits by `dependabot[bot]` and by
   `Claude <noreply@anthropic.com>`.

3. **Probe the machine.** Write the results into the session-log entry you
   will add at the end; they decide which tasks this session may take.
   ```sh
   uname -a
   ls -l /dev/kvm 2>&1                       # expected: absent
   docker info --format '{{.ServerVersion}}' 2>&1
   uv --version; bun --version; node --version
   curl -sS -o /dev/null -w '%{http_code}\n' https://pypi.org/simple/ 2>&1
   curl -sS -o /dev/null -w '%{http_code}\n' https://registry.npmjs.org/ 2>&1
   ```
   | Probe result | What it allows |
   |---|---|
   | `uv` works and PyPI answers | `uv sync` in `apps/server`, the backend's pytest where it needs no Docker |
   | `bun` and `node` work and npm answers | `bun install` in `apps/web`, Vitest, `astro check`, the build; Playwright only if its browsers install |
   | `docker info` answers | tasks whose Author tags include `docker`, with results marked `needs-local-verify` |
   | No `/dev/kvm` | No `kvm` task, ever. This is the expected case |

   If neither toolchain works, the session can still write docs and plan
   corrections; say so in the session log and keep to that.

4. **Read the ledger.** In `docs/plans/sandbox-implementation.md`: the
   header (PR number, active-session claim), the "Open" list in "Owner questions", the
   last three session-log entries and the task table.
   - **The claim.** If any session's claim is open, stop: report it and do
     no work. Two sessions on one branch produce conflicting ledgers. Only
     the owner can release someone else's claim.
   - **The last session-log entry's "Next".** If it names a task a cloud
     session can do, start there.

5. **Read the PR, without writing to it.**
   ```sh
   gh pr view <PR> --json isDraft,state,autoMergeRequest 2>&1
   ```
   If `gh` is unavailable, skip this. If the PR is no longer a draft, or
   has auto-merge on, stop and report: a push could merge unfinished work.

6. **Check `main` is merged in.** If `git rev-list --count
   HEAD..origin/main` is not zero, do not merge `main` yourself: merging
   can need Alembic and conflict work that the local plan assigns to the
   laptop. Work on the branch as it is, and note in the session log that
   `main` is ahead by that many commits.

7. **Claim.** In the ledger header set
   `Active session: cloud, <YYYY-MM-DDTHH:MMZ>, <task id(s)>` (UTC, as
   every session writes it), commit it alone (`docs(plans): claim the
   sandbox ledger for a cloud session`) and push (see "Pushing"). If the
   push fails because the branch moved, fetch, go back to step 4: someone
   else may have claimed it.

   **A claim only counts on the feature branch.** If this session can
   push only to a hand-off branch, no other session can see its claim.
   Then ask the owner in this session's chat whether any other session is
   working on the sandbox; work only after they say none is, and record
   their answer in the session log.

8. **Pick the task.** The first task in the table whose status is `todo`,
   that may be started under the implementation plan's "Dependency rule",
   whose
   **Author** tags are only `any` (or `docker` when the probe allows it),
   and which nothing in the "Open" list in "Owner questions" blocks. If there is none,
   the session's useful work is checking the plan against the code (below)
   and handing off.

## Working a task

1. **Read the task's section of the plan in full**, then check the paths,
   functions and line numbers it names against the code. Use the session's own read-only search agents
   (Explore or equivalent) for the lookups, in parallel when there are
   several. If the code has moved on from the plan (renamed functions,
   call sites gone or new), correct the task's instructions in the plan
   first, then build to the corrected text. If the drift changes a
   decision recorded in the proposal, do not decide it: add it to "Open
   owner questions", set the task `blocked`, and pick another.
2. **Build the smallest correct change** the task describes, reusing the
   repo's existing patterns. When the session offers subagents, give each
   one a bounded unit with no file overlap; do the integration yourself.
3. **Keep authoring and review apart.** After the change, have a separate
   agent review the diff for correctness and against AGENTS.md's rules
   before it is committed: the project's `reviewer` agent
   (`.claude/agents/reviewer.md`) when the session loads project agents,
   or a fresh general-purpose agent given the diff and AGENTS.md. Tasks the
   plan marks **security** get a second review focused only on the
   security boundary.
4. **Use the project skills** in `.claude/skills/` where the session loads
   them: `new-migration` for an Alembic revision, `docs-sync` before
   committing, `pr-gate` (its prediction step only; `make pr-gate` reads a
   PR, which is allowed, but its findings go in the ledger, not the PR).
5. **Verify what can be verified here.** Run each item of the task's
   **Verify** list that the probe allows, plus `uvx pre-commit run
   --files <changed files>`. For every item that cannot run here, write
   it into the task's ledger row as a numbered "local checks" list with
   the exact command. Never mark an item verified that did not run.
6. **Set the status.** `done` only when every Verify item ran here and
   passed and none needs the laptop; otherwise `needs-local-verify` with
   the list from step 5. A task that cannot finish this session is split
   in the ledger (T13a done, T13b `todo`) rather than left `in-progress`.
7. **Commit** in the same commit as the ledger update: a conventional
   message focused on the task, with no co-author trailer, no "Generated
   with" or "Generated by" line and no session link (AGENTS.md's commit
   policy; the `PR gate` reads every commit message).

## Pushing

Before every push, check that nothing the gate or the commit policy forbids
is in the new commits:

```sh
base=origin/<feature-branch>
git log "$base"..HEAD --format='%an <%ae>' | sort -u \
  | grep -v -x 'Eli Pittman <123281783+epittman23@users.noreply.github.com>' \
  && echo 'WRONG AUTHOR: FIX BEFORE PUSHING' || echo 'authors ok'
git log "$base"..HEAD --format='%B' \
  | grep -n -i -E 'co-authored-by|generated (with|by)|claude\.ai/code|noreply@anthropic' \
  && echo 'ATTRIBUTION: FIX BEFORE PUSHING' || echo 'messages ok'
```

Every author line must be exactly the owner's identity in "Fixed names".
If not, fix the unpushed commits before pushing. For the last commit
alone: `git commit --amend --reset-author --no-edit`. For several:
`git reset --soft origin/<feature-branch>` (or the hand-off
branch's remote tip), then commit the work again under the right identity,
one commit per task as before. Neither rewrites anything already pushed,
which is the history the no-rebase rule protects.

Then push to the feature branch:

```sh
git push origin HEAD:<feature-branch>
```

If the platform refuses that ref, push the hand-off branch instead
(`git push origin HEAD`) and name it in the session log, so a local session
can merge it. Never open a pull request for it, not even a draft into the
feature branch: the platform would put its footer in the body, and a
non-draft PR from a branch of this repository auto-merges.

## Session end

1. Append a session-log entry to the ledger:
   `<date> | cloud | <tasks touched> | <what happened; the probe's results; the hand-off branch, if any> | Next: <the exact next action, and whether it needs the laptop>`.
2. Clear the claim (`Active session: none`).
3. Commit (`docs(plans): hand off the sandbox ledger`), check, and push as
   above.
4. In the final reply to the owner, say: the tasks touched and their new
   statuses, what still needs the laptop (the "local checks" lists), any
   new owner question, and the hand-off branch if one was used.

## When the plan and the code disagree, or nothing fits

- **Plan drift** is fixed in the plan, in a `docs(plans): ...` commit,
  before code is written to it. That correction is useful work in itself
  and can be a whole session.
- **No task fits** this machine: check the next two or three local tasks'
  instructions against the current code and correct them, so the next
  laptop session starts on accurate instructions. Record that in the
  session log.
- **A decision is needed:** add it to the "Open" list in "Owner questions" with the
  options and a recommendation, and stop that task. The owner answers in a
  later session; a cloud session never decides one.

## Hard rules

- Never write to the pull request, its labels or its auto-merge setting.
- Never bypass or weaken the CI tripwire in any way (AGENTS.md, "The CI
  tripwire"); gate findings are recorded in the ledger for the local
  session to justify in the PR body.
- Never rebase, force-push, or push to `main`.
- Never edit an Alembic revision that a ledger row says was applied to the
  laptop's database, a benchmark prompt file, or an existing
  `docs/decisions.md` entry on `main`.
- Never mark a check verified that did not run in this session.
