# Sandbox implementation: running a local session

> **To start a session**, open Claude Code in `~/local-llm` and say:
> "Resume the sandbox work by following `docs/plans/sandbox-sessions-local.md`
> on the `feat/sandbox-harness` branch." From T40 on, name
> `feat/sandbox-remove-jupyter` instead.

How an agent session on the owner's laptop picks up the sandbox work where
the last session left it, drives it forward with the oh-my-claudecode (OMC)
plugin, and hands it on. It says nothing about what to build: that is
[sandbox-implementation.md](sandbox-implementation.md), the one
implementation plan, which both local and cloud sessions follow. Cloud
sessions follow [sandbox-sessions-cloud.md](sandbox-sessions-cloud.md)
instead of this file.

Written 2026-11-10, against OMC 5.7.14 (`omc --version`). The design being
implemented is [docs/proposals/sandbox-code-interpreter.md](../proposals/sandbox-code-interpreter.md).

## The three files and which one wins

| File | Holds | Who edits it |
|---|---|---|
| `docs/plans/sandbox-implementation.md` | What to build, task by task, and the **ledger**: every task's status, commit and evidence, the active-session claim, the session log, open owner questions | Every session, local or cloud, in the same commit as the work it records |
| `docs/plans/sandbox-sessions-local.md` (this file) | How a local session runs | Only to fix the procedure; such a fix is its own commit |
| `docs/plans/sandbox-sessions-cloud.md` | How a cloud session runs | Same |

**The committed ledger on the feature branch is the only record of
progress.** OMC keeps its own state under `.omc/` (the ultragoal ledger,
the notepad, project memory), but `.omc/` is gitignored: it never reaches a
cloud session, a fresh clone or another worktree, and it is lost when a
worktree is removed. Treat OMC state as this laptop's working copy. When it
disagrees with the committed ledger, the committed ledger is right and OMC
is corrected to match, never the other way round.

The copies of these files on `main` are stale by design while the work is
under way; always read the copies on the feature branch.

## Fixed names

| Thing | Value |
|---|---|
| Feature branch | the branch of the layer the next task belongs to, from the ledger header's table: `feat/sandbox-harness` for T30-T39, `feat/sandbox-remove-jupyter` for T40-T49 (`<feature-branch>` in the commands below) |
| Pull request | that layer's draft PR, one of four stacked PRs (split from the single PR #884 on 2026-11-13); each number is in the ledger header's table |
| PR titles | one per layer, as the PRs carry them; each PR's body has the layer table. Never retitle a PR to the single-PR title used before the split |
| OMC ultragoal plan id | `sandbox` (pass `--plan-id sandbox` to every `omc ultragoal` command) |
| Ultragoal goal mode | `per-story` (one `/goal` per task, so a session can stop when its task is done) |

## What only a local session does

Cloud sessions can write code and docs, but some work needs this laptop or
the owner. A local session owns all of it:

- **Opening the draft PR (T00) and editing its body.** The PR body carries
  the `## Gate changes` section and must never carry a session link or a
  "Generated by" footer, which a cloud platform adds to PRs it opens and
  the `PR gate` check rejects.
- **Tasks whose Author or Verify tags include `docker`, `kvm`, `gpu`,
  `host-internet`, `local` or `owner`** in the implementation plan (see
  its "Requirement tags"): building images, the
  wheelhouse download, Kata on the host, the acceptance tests, the harness
  baseline on the GPU, anything needing `sudo`.
- **Verifying cloud work.** A task a cloud session finished is left at
  `needs-local-verify` with the checks it could not run; a local session
  runs them and only then sets it to `done`.
- **Merging hand-off branches.** If a cloud session could not push to the
  feature branch, it pushed a `claude/*` branch and named it in the session
  log; a local session merges it.
- **Merging `main` into the feature branch**, and the Alembic work that
  can follow (see "Keeping up with main").
- **Asking the owner to mark the PR ready** at the very end (T49).

## Session start (the resume protocol)

Do these in order before touching any code. Each step is cheap; skipping
one is how sessions continue on the wrong branch or redo finished work.

1. **Orient.**
   ```sh
   pwd
   git status --short --branch
   git worktree list
   ```
   Work in the main checkout (`~/local-llm`) unless the owner says
   otherwise. A linked worktree has its own `.omc/`, and `make backend`
   from two checkouts fights over the same ports and Compose project. If
   the tree is dirty with changes that are not yours, stop and ask the
   owner.

2. **Get the branch.**
   ```sh
   git fetch origin --prune
   git switch <feature-branch>
   git merge --ff-only origin/<feature-branch>
   ```
   If the fast-forward fails because both sides have commits, merge
   (`git merge origin/<feature-branch>`). Never rebase this
   branch and never force-push it: cloud sessions and the PR both build on
   its history.

3. **Look for cloud hand-offs.**
   ```sh
   git branch -r --list 'origin/claude/*'
   ```
   Compare with the session log in the implementation plan. A hand-off
   branch named there and not yet merged gets merged now (`git merge
   origin/claude/<name>`), then its tasks are verified like any other
   `needs-local-verify` task. Do not delete remote branches; tell the owner
   they can be deleted.

4. **Read the ledger.** In `docs/plans/sandbox-implementation.md`, read the
   header (PR number, active-session claim), the "Open" list in "Owner questions", the
   last three session-log entries and the task table. Note:
   - **The claim.** If another session's claim is open and less than 24
     hours old, stop and ask the owner whether that session is still
     running. If older, ask the owner before taking it over.
   - **Owner questions** that block the task you would take next.
   - **The "Next" line** of the last session-log entry: that is where the
     last session wanted the next one to start.

5. **Check the PR.**
   ```sh
   gh pr view <PR> --json isDraft,state,autoMergeRequest,labels,mergeStateStatus
   ```
   It must be an open draft with no auto-merge. If it has turned ready, or
   auto-merge is on, do not revert it: the owner may have done it on
   purpose. Stop and ask the owner before any push, because a push to a
   ready PR with auto-merge on can merge unfinished work.

6. **Reconcile OMC with the ledger.**
   ```sh
   omc ultragoal status --plan-id sandbox
   ```
   - **No plan** (new checkout, or `.omc/` was cleaned): create one from
     the ledger's unfinished tasks, one goal per task, in table order,
     **leaving out T49** (owner-only, never an agent story) so that T48 is
     the last story and carries OMC's final quality gate:
     ```sh
     omc ultragoal create-goals --plan-id sandbox --claude-goal-mode per-story \
       --brief "Implement docs/proposals/sandbox-code-interpreter.md per docs/plans/sandbox-implementation.md" \
       --goal "T10::T10 per docs/plans/sandbox-implementation.md: every Verify item has evidence and the ledger row is done or needs-local-verify" \
       --goal "T11::T11 per docs/plans/sandbox-implementation.md: ..."   # one per unfinished task
     ```
     Write each objective as that completion condition, not just the
     task's title: it becomes the `/goal` the owner types. Tasks already
     `done` in the ledger are not added.
   - **Plan exists but disagrees** (a task done in the ledger is still
     pending in OMC, or the ledger has rows OMC lacks): rebuild it. OMC
     only checkpoints the goal that is active and in progress, so finished
     tasks cannot be ticked off from outside a story. Run the
     `create-goals` command above again with `--force`, from the ledger's
     unfinished rows. For a row added to the ledger since (a split task, a
     blocker), `omc ultragoal add-goal --plan-id sandbox --title ...
     --objective ...` is enough. Never change the ledger to match OMC.
   - **Goal ids.** OMC names goals `G001-t10`, `G002-t11`, and so on, from
     their order and the text before `::`. Map ledger IDs to goal ids with
     `omc ultragoal status --plan-id sandbox --json` before any
     `complete-goals` or `checkpoint`.
   - If `omc` is not on `PATH`, use
     `node ~/.claude/plugins/cache/omc/oh-my-claudecode/<version>/bin/oh-my-claudecode.js`
     in its place.

7. **Read local notes.** `notepad_read` (OMC's notepad) for anything a
   previous local session left for this laptop only. Anything another
   session needs belongs in the ledger, not here.

8. **Keep up with `main`** if it has moved (see below), before claiming,
   so the claim commit sits on a current branch.

9. **Refresh the code graph** with the project's `reindex` skill. Graph
   answers about a branch you just merged into are stale until it runs.

10. **Claim the session.** In the ledger header set
    `Active session: local, <YYYY-MM-DDTHH:MMZ>, <task id(s)>` (UTC, as
    every session writes it; `date -u +%FT%RZ`), commit it
    alone as `docs(plans): claim the sandbox ledger for a local session`,
    and push. The claim is what tells a cloud session started meanwhile to
    stand off.

11. **Pick the task.** The next task is the first one in the table whose
    status is `todo` or `needs-local-verify`, that may be started under
    the implementation plan's "Dependency rule", and whose Author and
    Verify tags this session can meet (a
    laptop session meets all of them but `owner`). A task tagged
    `owner` needs the owner at the keyboard: ask with AskUserQuestion
    before starting it, and pick another task if they are not available.
    Prefer `needs-local-verify` tasks first, so unverified work does not
    pile up under new work.

## Working a task

### Start the story

```sh
omc ultragoal complete-goals <goal-id> --plan-id sandbox
```

This prints a handoff. Its `/goal` cannot be set by the agent: ask the
owner to type `/goal <the objective it printed>` and wait. OMC's
PreToolUse guard blocks tool calls until a `/goal` is active, so nothing
else can happen until they do. Set the task's ledger status to
`in-progress` (no separate commit; it goes in with the work).

### Read before writing

Read the task's section of the implementation plan in full, then check the
paths, functions and line numbers it names against the code: `explore` agents (or the codebase-memory
graph) for "where is X now", in parallel when there are several lookups.
**If the code has moved on from what the plan says** (a renamed function,
a call site that is gone, a new one), fix the plan first: update the task's
instructions in `sandbox-implementation.md`, then build to the corrected
text. Use the `planner` agent (`model=opus`) when the drift changes the
task's design rather than just its paths, and ask the owner when it changes
a decision recorded in the proposal.

### Agent lanes

Authoring and approval are separate passes in separate agents. The agent
that wrote a change never approves it.

| Work | OMC lane | Model |
|---|---|---|
| Lookups, call-site sweeps | `explore` | default (haiku-class is fine) |
| Redesign after plan drift | `planner` | `opus` |
| Backend code: manager, backends, tools, call sites, migrations | `executor` | `opus` for `sandbox/` and anything on the security boundary; `sonnet` otherwise |
| Tests written before or beside the code | `test-engineer` | `sonnet` |
| Frontend output rendering, settings UI | `designer` for layout, then `executor` for wiring | `sonnet` |
| Failures that do not yield to one fix | `debugger`, or `tracer` for competing hypotheses | `sonnet` |
| Docs and guides | `writer`, checked against the code by the author's reviewer | `sonnet` |
| Review of the diff | `code-reviewer`, through the `review` skill (its standards and intent axes) | `opus` |
| Security review | `security-reviewer`: required for tasks marked **security** in the plan (the backends, tools, uploads, Compose networks, output rendering, the raw-download endpoint) | `opus` |
| Evidence that it works | `verifier`, through the `verify` skill | `sonnet` |
| Pre-PR review against this repo's rules | the project's own `reviewer` agent (`.claude/agents/reviewer.md`) | default |

Run independent units in parallel (the `execute` skill's rule), but never
two authoring agents on the same file, and never more than two `executor`
agents at once: the laptop also runs Docker, the backend and sometimes
`llama-server`. Do not use `team`, `autopilot` or `ralph` loops for this
work; each task is one bounded story, and the ultragoal
ledger already provides the loop.

### The project's own skills

Use them where they apply; they encode rules CI cannot check.

- **`new-migration`** for every Alembic revision (config defaults, the
  `sandbox_package_events` table, the engine-row migration).
- **`docs-sync`** before every commit that changes behaviour, layout,
  settings, Makefile targets, routes or a decision.
- **`pr-gate`** before every push: predict the findings, and keep the PR
  body's `## Gate changes` section current (see below).
- **`serving-change`** only if a task touches `benchmarks/serving/` (none
  is expected to; the harness is not serving).
- **`reindex`** after every merge.

### Verify

Every task in the implementation plan ends with a **Verify** list. Run all
of it, through the `verifier` agent or directly; the task is not done until
each item has evidence (a command and its result, a test name, a
screenshot path). Always also run the narrowest `make` targets the change
touches (`make test-backend`, `make test-web`, `make test-e2e`,
`make test-desktop`, `make test-types`, `make lint`), and `make check` at
the end of each migration step (tasks T29, T39, T48).

Checks tagged `kvm` need the real Kata runtime. Their checks never run in
CI; record their output in the ledger's evidence column, with the date and
commit, the way the proposal's acceptance tests ask.

### Review

After Verify passes, run the `review` skill: `code-reviewer` on the task's
diff (`git diff <task start>..HEAD`), plus `security-reviewer` when the task
is marked **security**. Fix blocking and should-fix findings with a fresh
`executor`, then review again. Record unfixed findings the owner should see
in the "Open" list in "Owner questions".

### Checkpoint and commit

1. Update the ledger in the same commit as the work: status `done` (or
   `blocked`, `needs-local-verify`), the evidence, and anything the next
   task must know. Leave the Commit column empty: a commit cannot name its
   own sha. The session-end commit fills it in for every task finished in
   the session.
2. Commit with a conventional message focused on the task, for example
   `feat(sandbox): add the per-chat SandboxManager`. No co-author trailer,
   no "Generated with" line, no session link (the commit policy; the
   `PR gate` check reads every commit message).
3. Checkpoint OMC. A per-story checkpoint needs a snapshot of the
   session's `/goal`, which must show the story's objective, verbatim, as
   complete (ask the owner for the `/goal` status if it is not in view):
   ```sh
   omc ultragoal checkpoint --plan-id sandbox --goal-id <goal-id> \
     --status complete --evidence "<commit sha>; <verify summary>" \
     --claude-goal-json '{"goal":{"objective":"<the story objective, verbatim>","status":"complete"}}'
   ```
   OMC's statuses are not the ledger's, so map them like this:
   - ledger `done` or `needs-local-verify`: OMC `complete`, as above.
   - **Unfinished at session end** (ledger `in-progress`, with a
     session-log line): no checkpoint. Leave the goal in progress; the next
     session's `complete-goals` with no id resumes it.
   - **The approach failed and must restart** (ledger `blocked` or `todo`
     with the reason): `--status failed`; the next attempt starts with
     `complete-goals <goal-id> --retry-failed`.
   - Never use `--status blocked`: in OMC it means only that a different,
     completed `/goal` is in the way, and it needs that goal's snapshot.
4. Push: `git push origin <feature-branch>`.
5. `make pr-gate PR=<PR>` (read-only). A finding not yet in the plan's
   "Expected PR gate findings" is a stop: add it there and to "Open owner
   questions", and ask the owner about it (AGENTS.md, "The CI tripwire")
   before building on it. Every finding goes under `## Gate changes` in
   the PR body with its justification (step 3 of "Pull request body"
   below).

One task per commit is the default. A task too large for one session is
split in the ledger (T13 becomes T13a, T13b) before the session ends, not
left half done under one ID.

## Keeping up with main

`main` keeps moving while the branch is open, and a draft PR is not kept up
to date automatically in every case (see the testing guide's "Merging,
auto-merge and branch updates"). At each session start, if
`git rev-list --count HEAD..origin/main` is not zero, merge it into the
bottom open layer of the stack first (the ledger header's table), then
merge each layer into the one above it, up to the feature branch:

1. `git merge origin/main`, resolving conflicts in favour of `main`'s
   intent and re-applying the branch's change on top. Never rebase. Set
   the ledger's "`main` last merged in at" to the merged `main` sha.
2. **Alembic heads.** `main` may have added revisions since the branch's
   were written. Check for a single head (the `new-migration` skill shows
   how). If there are two, add an Alembic merge revision with the
   `new-migration` skill rather than editing a branch revision's
   `down_revision`: a branch revision may already be applied to the
   laptop's database, and editing an applied revision is what the
   append-only rule forbids.
3. Re-run the tests the conflicted files touch, then `make check` if the
   merge touched anything outside `docs/`.
4. `reindex`.
5. Commit the merge (`git commit --no-edit` keeps git's message, which is
   fine inside a branch; the squash merge replaces it).

## Pull request body

Only a local session edits it (`gh pr edit <PR> --body-file <file>`, from a
file in the scratchpad). It holds, in order:

1. One paragraph on what the PR does, pointing at the proposal and the plan.
2. `## Progress`: the ledger's task IDs and statuses, copied from the
   ledger at each push (the ledger stays the source; this is a view).
3. `## Gate changes`: every `PR gate` finding the branch produces, each
   with why the change is needed and why it does not weaken what CI
   catches, as AGENTS.md's "The CI tripwire" requires. The implementation
   plan's "Expected PR gate findings" lists the ones known in advance; add
   any others `make pr-gate` reports.
4. `## Laptop checks`: the acceptance-test results, with dates and commits,
   as they are recorded.

The body becomes the squash commit's message, so it must stay free of
session links and attribution lines.

## Session end

Leave the branch so that a cold start, local or cloud, can continue from
the ledger alone.

1. Finish or checkpoint the current task (above). Never leave a task
   `in-progress` without a session-log line saying what is half done and
   where.
2. Fill in the Commit column for every task finished this session (the
   sha of the commit that did the work), then append a session-log entry
   to the ledger:
   `<date> | local | <tasks touched> | <what happened> | Next: <the exact next action>`.
3. Clear the claim (`Active session: none`).
4. Commit (`docs(plans): hand off the sandbox ledger`) and push. Update the
   PR body's `## Progress`.
5. Stop what this session started: `make backend` (Ctrl-C once; never
   twice), any `llama-server` started for the harness, sandbox containers
   left by manual tests (`docker ps --filter label=lllm.chat`). Ask before
   stopping anything this session did not start.
6. `/oh-my-claudecode:cancel` if any OMC mode is still active, so the next
   session does not inherit a stale loop. Write laptop-only notes with
   `notepad_write_working`.

## The final gate (T48, T49)

The last two tasks close the PR, and they are where shortcuts cost most.

1. Every task is `done`; no task is `needs-local-verify`; every acceptance
   test in the proposal is checked off with its date and commit in the
   PR body's `## Laptop checks`.
2. `make check` passes on the branch's head.
3. The ultragoal final-story quality gate, on T48's checkpoint:
   `ai-slop-cleaner --review` (review-only), the `verify` skill and the
   `review` skill, all clean. OMC refuses the final checkpoint unless
   `--quality-gate-json` holds `aiSlopCleaner.status` `"passed"` with
   non-empty `evidence`, `verification.status` `"passed"` with a non-empty
   `commands` list, and `codeReview.recommendation` `"APPROVE"` with
   `codeReview.architectStatus` `"CLEAR"`. A finding becomes a blocker
   story (`omc ultragoal record-review-blockers --plan-id sandbox
   --goal-id <T48's id> --title ... --objective ... --evidence
   "<findings>" --claude-goal-json '<the active /goal snapshot>'`) and a
   ledger row, never a footnote.
4. The project's `reviewer` agent on the whole branch; its blocking and
   should-fix findings are fixed or put to the owner.
5. `make pr-gate PR=<PR>`: every finding is listed and justified under
   `## Gate changes`.
6. Merge `main` in one last time, so the branch is up to date, and re-run
   the Kata suite and `make check` if the merge touched anything outside
   `docs/`.
7. Ask the owner (AskUserQuestion) to review the `## Gate changes`
   section, mark the PR ready and add the `gate-change-approved` label.
   Only the owner does these, unless they explicitly tell the agent to do
   one of them for this PR. Marking it ready turns auto-merge on, and from
   then on `update-branches.yml` merges `main` into the branch whenever
   `main` moves (docs/guides/testing.md, "Merging, auto-merge and branch
   updates"). Every new commit, the bot's included, removes the label, so
   the owner approves only when the branch is up to date and approves
   again after any update. Nothing is pushed after the owner's approval
   without asking them again; if a bot update merges code from `main`,
   re-run the checks the merged files touch before asking for the new
   approval.

## Hard rules

- Never bypass the CI tripwire: no label, no admin merge, no edits to the
  gate's workflow, script or patterns, no rewording to slip past it,
  without the owner's explicit yes for this PR at this commit (AGENTS.md).
- Never mark the PR ready, turn on auto-merge, or merge it.
- Never rebase or force-push the feature branch.
- Never edit an Alembic revision that has been applied to a database, a
  benchmark prompt file, or an existing `docs/decisions.md` entry on
  `main`.
- Never run a sandbox container with options built from model- or
  user-provided strings while testing; the plan's backend task explains why.
- Decisions belong to the owner. Ask with AskUserQuestion, one focused
  question, and record the answer in the proposal's Decisions table and
  the ledger.
