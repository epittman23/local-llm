# Assistant tools: code interpreter, web search, retrieval

The services and models behind three of the assistant's tools, added on
2026-10-24. The services run from `infra/docker-compose.yml` and start and
stop with `make backend`. The settings that point the app at them live in
the app's database (Admin Settings), not in a repo file.

## Code interpreter: Jupyter

The app's code interpreter has two engines.

- **Pyodide** (the inherited default) runs Python in the browser. The
  backend only relays the code to the page and waits, so nothing runs
  without a browser tab open, and the package set is Pyodide's.
- **Jupyter** runs on the server. The backend opens a kernel, runs the
  block, returns stdout, stderr and the result, and deletes the kernel.
  This is the only engine a request without a browser can use, such as a
  benchmark item sent through the app.

The `jupyter` service is `quay.io/jupyter/scipy-notebook:2026-10-12`: Python
3.13 with pandas, numpy, scipy, statsmodels, scikit-learn, sympy, matplotlib
and seaborn. It listens on `127.0.0.1:8888` and needs `JUPYTER_TOKEN` from
`infra/.env` (generated by `make backend` when missing).

It runs code a model wrote, so it is fenced in:

- its own Docker network: it cannot reach Postgres, Redis or SearXNG by
  name, and the host's loopback-only ports (Postgres, Redis, the backend,
  `llama-server`) refuse it;
- an unprivileged user, no Linux capabilities, `no-new-privileges`;
- 4 GB of memory and 512 processes at most;
- no terminals; kernels idle for 10 minutes are culled.

It **can reach the internet**, so `pip install` works inside a block. To
cut that off, set `internal: true` on the `jupyter` network in the Compose
file.

These were checked on 2026-10-24: from inside the container, every service
name failed to resolve and the gateway's ports 4000, 5432, 6379, 8080 and
8090 refused connections, while `https://pypi.org` answered.

Two limits of the Jupyter engine to know:

- **No state between blocks.** Each code block gets a fresh kernel, so a
  variable defined in one block is gone in the next. A model has to repeat
  its setup (imports, loading data) in each block.
- **Uploaded files do not reach it.** The Pyodide engine is given the
  chat's attached files; the Jupyter engine is given only the code. A CSV
  attached to a chat cannot be read from a Jupyter block yet.

**Settings** (Admin Settings > Code Execution): set both the code
interpreter's and code execution's engine to `jupyter`, the URL to
`http://127.0.0.1:8888`, authentication to `token`, and the token to
`JUPYTER_TOKEN`'s value.

## Web search: SearXNG

The `searxng` service is `searxng/searxng:2026.10.17-1c10abe2d`, on
`127.0.0.1:8080`, with its secret from `infra/.env` (`SEARXNG_SECRET`,
generated by `make backend` when missing). `infra/searxng/settings.yml`
holds only what differs from SearXNG's defaults: JSON output on, which the
backend needs, and the limiter off, which needs a Redis of its own.

**What it does and does not keep private.** SearXNG needs no API key and
no account, and sends no cookies. But it is a metasearch engine: each query
still goes to the upstream engines it asks (Google, Bing, DuckDuckGo and
others), from this machine's IP address. Those engines see the query,
without knowing which user or chat it came from. Upstream engines also
rate-limit it now and then. On 2026-10-24 a query returned 20 results
while Brave and DuckDuckGo did not answer.

**Settings** (Admin Settings > Web Search): turn web search on, set the
engine to `searxng` and the query URL to
`http://127.0.0.1:8080/search?q=<query>`.
